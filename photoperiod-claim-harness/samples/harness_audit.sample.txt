2  C1's numbers are narrower than its reads line
========================================================================
  signature cells                      58
  kWh per dry gram, ratio to control   0.1439 .. 0.7027
  cells with ratio >= 1.0              0
  signature_no_dry_gain_cells          0

  The S1 docstring names the cell it is hunting for:

      A cell where (a) is TRUE and (b) is FALSE is a configuration
      in which the whole reported package appears with no gain per
      unit photosynthate.

  It finds none. Every one of the 58 cells that reproduces the
  signature also improves energy per dry gram -- the whole range
  sits below 1.0.

  So the reads line for FALSE overstates by one word. It says the
  signature is NON-DIAGNOSTIC. What the grid shows is that it is
  non-diagnostic of MAGNITUDE -- a 4.9x range in the true ratio --
  and diagnostic of SIGN. On this mechanism set the reported
  package does license 'cheaper per dry gram'; it does not license
  any particular number, and 68% is a number.

  That is a stronger claim than the one written, because it
  survives the objection that the sim was rigged to find nothing.
  It found the effect and still cannot size it.

  REPAIRED, by updating the CLAIM rather than the sim -- which is
  what the protocol says to do. C1's reads line now separates
  MAGNITUDE from SIGN and names the field that backs it:

      signature_sign_agreement = 1.0
      signature_cells_below_1  = 58 of 58

  The field is None when there is nothing to agree on, so it
  cannot be read as unanimity in the empty case section 1 covers.

3  the edit guard reads 2 of 4 fields
========================================================================
  MechanismEdit takes four free-text fields:  reason, mechanism, basis, prediction

  and screens `reason + " " + mechanism` against FORBIDDEN_REASONS.

  field        outcome when it carries a forbidden reason
  --------------------------------------------------------------
  reason       refused
  mechanism    refused
  basis        refused
  prediction   refused

  `basis` and `prediction` are the two fields a motivated editor
  would put the outcome reasoning in, because they are the two
  that ask for justification. The screen is on the two that ask
  what changed.

  REPAIRED: the screen reads the concatenation of all four.

  Worth saying what the guard gets right: it is a PRE-registration
  gate, it fires at construction rather than at settle time, and
  the refusal message names the protocol. Refusing on a substring
  is crude and it is a real deny branch, which most such rules
  are not.

4  settle() used to record a prediction and never adjudicate it
========================================================================
  Pre-repair, settle(observed) wrote:

    prediction_held   None   # 'human or model fills this in'
    file_hash_after   equal to file_hash_before, unremarked

  So a registered prediction could be settled with the
  comparison never made, and the protocol -- which exists to gate
  SIM EDITS -- could not tell whether the edit it gated had
  happened. An edit registered, settled and never performed was
  indistinguishable in the log from one carried out.

  REPAIRED. Three behaviours, each demonstrated:

    settle without a verdict               refused: REFUSED: settle(observed, held) re
    settle with a non-bool                 refused: REFUSED: settle(observed, held) re
    settle an edit that did not happen     refused: REFUSED: file hash unchanged, so n
    abandon(reason)                        logged as MECHANISM_EDIT_ABANDONED
      file_changed = False

  `abandon` is the path for an edit decided against, so the trail
  stays intact either way -- registered, then not made, and the
  log says which.

  Same shape as ../reasoning-gate/'s declared control that was
  never scored. Its repair was to refuse an empty observation and
  write a record either way; this is that, on a prediction.

6  what the harness gets right
========================================================================
  The predicates are real. Every claim in the table is a function
  of a sim output and can come back either way -- and four of the
  five come back REFUTED on the shipped run, including two the
  file's own framing would have preferred to support.

    C1   [REPORTED] REFUTED
    C2   [PHYSICS ] REFUTED
    C3   [PHYSICS ] REFUTED
    C4   [PHYSICS ] REFUTED
    C5   [PHYSICS ] SUPPORTED

  C2 is the sharpest thing in the file. It states a PREMISE from
  the literature (angiosperms have POR only, no DPOR), then a
  HYPOTHESIS that dark could still help by recharging the pool,
  then refutes its own hypothesis -- and the reads line for FALSE
  explains WHY in mechanism terms: the FLU clamp acts on pool
  SIZE, so a full pool slows synthesis and draining it
  continuously maximises flux. Then it NAMES the next candidate
  (shade acclimation) and files it in PENDING_EDITS rather than
  retuning.

  PENDING_EDITS is the part with no equivalent elsewhere in this
  repository. Three mechanisms named, each with a basis and a
  prediction registered BEFORE any run, all marked UNRUN. That is
  the alternative to quietly retuning a sim that came out the
  wrong way, written down as a data structure.

  Provenance is separated at the type level -- REPORTED, PHYSICS,
  SIM, BENCH -- and the hypothesis block says plainly that every
  number in it is SIM, that a sim can show an artifact is
  SUFFICIENT to produce a signature and not that it happened, and
  that the confidence and comfort readouts are separate and are
  not filled in by the file.

  BENCH is declared and no code path can emit it. That is the
  honest state and the file says so; the protocol section is the
  instructions for producing one, which is more than most claim
  tables carry.

8  three things the README described that the code did not do
========================================================================
  The repairs above were chosen by one rule: make the code do
  what the delivered README already says it does. Three of them
  were promises with no implementation at all.

  (a) 'run -> provenance record -> RESIDUAL ROUTER -> hypothesis
      block'. residual_route() was defined and never called.

      C2 REFUTED    residual_route attached: True
      C5 SUPPORTED  residual_route attached: False

      It attaches where it is the point -- a claim that did not
      hold, or one the predicate could not decide. Four questions,
      unanswered by construction. The router routes; it does not
      resolve.

  (b) 'Provenance never merges: REPORTED, PHYSICS, SIM, BENCH.
      BENCH is empty until someone runs one.' Three types had
      code paths. BENCH was declared and unreachable, so 'empty'
      was true by absence rather than by construction.

      before: 0 BENCH record(s)
      after:  1 BENCH record(s)
      a number with no method: refused -- that is SIM
                               provenance wearing a BENCH
                               label

      The hypothesis block now reports BENCH coverage per claim,
      so 'no physical exit yet' is a printed line rather than an
      absence the reader has to notice.

  (c) the hypothesis block stamped the wall clock one line above
      the file hash it printed for provenance, so two runs of the
      same file produced two different documents.

      identical across two calls: True
      run id: d6b15e6cbe44

      The id is the file hash plus the claim statuses, so it moves
      when either does and not otherwise. The clock is in the log,
      where every record already carries one.

========================================================================
READING
========================================================================

  REPAIRED, all of it, pinned by tests/test_repairs.py. The rule for what
  to fix was the delivered README: make the code do what the prose already
  says it does.

  C1's predicate returned SUPPORTED -- "the reported metrics are
  diagnostic" -- from a run in which the sim reproduced the signature zero
  times, because the spread of an empty set was 0.0. It now calls
  require() and routes to UNDECIDED, the third verdict run_claim() always
  had a branch for. The README's own extension rule is what this restores:
  a predicate that can fail.

  C1's reads line was updated rather than the sim, which is what the
  protocol says to do. The grid finds the signature in 58 cells spanning a
  4.9x range of true energy-per-dry-gram and ALL of them below 1.0, so it
  is non-diagnostic of magnitude and diagnostic of sign. signature_sign_-
  agreement carries that, and is None when there is nothing to agree on.

  The edit guard screens all four fields it is given. settle() requires a
  bool and refuses when the file hash has not moved, with abandon() as the
  path for an edit decided against -- so a registered, settled,
  never-performed edit is no longer indistinguishable in the log from a
  real one.

  The dark-interval readout is a cycle average, so the curve is monotone
  and the README's C3 sentence is true of the output for the first time.
  Registered as an InstrumentEdit: the protocol governed MECHANISM changes
  and had no category for a change to where a number is READ, which alters
  sim output while altering no mechanism. No verdict moved.

  And three promises with no implementation: the residual router is in the
  pipeline, BENCH has an ingest path that refuses a number with no method,
  and the hypothesis block carries a deterministic run id instead of a wall
  clock stamped one line above the hash it prints for provenance.
