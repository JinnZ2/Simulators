  WHAT THIS AUDIT GOT WRONG, kept on record. Three failures were
  predicted from the README before any of it was run. Two were
  refuted by the code, both in the direction that makes the
  delivered instrument look better:
    always 'member'
      predicted IDEAL-MATCHER (both axes)
      actual    RUN INVALID
      the control gate catches it first -- 2 of 4 controls are not_member, so ctrl_ok = 0.50 and the run is voided before the traps are read
    always 'uncertain'
      predicted CONSTRAINT READER
      actual    RUN INVALID
      same gate: uncertain is not correct on a control either, so ctrl_ok = 0.00. The hedge gap is real but narrower -- it needs a checker that answers the controls and hedges only the traps

  So the CONTROL GATE is stronger than it looks. It catches every
  constant-answer checker on its own, before a single trap is
  read, because no constant answer can be right on controls that
  run both ways. That also narrows the README's stated case for
  trap_b -- 'without it, a checker that says member to everything
  scores clean on trap_a' names a checker the gate already stops.
  trap_b's real job is the name-dropper row: coherent on
  controls, matcher-direction on traps. That checker passes the
  gate, passes trap_a, and is caught by trap_b alone. The
  conclusion holds; the example given for it does not.

  TWO GAPS SURVIVE, and both are checkers that answer nothing
  about the traps while being cleared to do constraint work.

  `uncertain` is unscored and ungated. A checker that answers the
  controls and hedges every trap, in constraint-shaped prose,
  reaches CONSTRAINT READER -- 'Safe to hand constraint-set work
  to this checker.' The README says a high hedge count with low
  coverage is the same defect wearing a hat and that the report
  says so; it says so only in the low-coverage branch, and the
  hat fits better with the coverage high.

  MISSING is not gated either, and needs no prose at all. A
  checker that answers the controls and skips every trap reaches
  the same verdict: the traps contribute no errors because they
  contribute no rows, and mean_cov() drops MISSING before
  averaging, so the mean is taken over the controls -- which the
  README itself says have thin constraint sets that even the
  synthetic matcher scores 1.00 on.

  Both are the same shape: an unanswered trap is scored as an
  absent error rather than as an absent answer. Twelfth instance
  in this repo of absent-vs-known-negative, and the repair is the
  one this tree keeps reaching for -- a third state, and a
  minimum answered-trap count in the gate beside ctrl_ok.
